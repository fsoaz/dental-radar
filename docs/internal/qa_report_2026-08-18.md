## Prioritized Issue Register

### NEW-1 · Scoring Settings page shows a nonsensical, unhelpful error for every validation failure

- **Domain:** Error Handling / Cross-Feature Consistency
- **Severity:** High
- **Priority:** P1
- **Summary:** A generic-message rewrite added for the `/clinics` list page's malformed-query-param errors (P2-13's fix) lives in the *shared* HTTP client and fires for every 4xx `VALIDATION_ERROR`, including scoring-config saves — replacing the backend's specific, actionable message with "That link isn't valid — reset filters and try again."
- **Steps to reproduce (verified by code trace against a live 422 response, not DOM-observed — browser unavailable this session):**
  1. Reproduced live: `PUT /scoring-config` with a band gap returns `422 {"error":{"code":"VALIDATION_ERROR","message":"bands leave a gap or overlap between 10 and 50", ...}}` (captured this session).
  2. Trace `frontend/lib/api.ts:request()`: line 74–76 correctly extracts that message from `body.error.message` and sets `code = "VALIDATION_ERROR"`.
  3. Line 96–98 unconditionally overwrites it: `if (response.status >= 400 && response.status < 500 && code === "VALIDATION_ERROR") { message = "That link isn't valid — reset filters and try again."; }` — with no check on which endpoint was called.
  4. `frontend/components/scoring-settings-client.tsx:96` (`save()`'s catch block) sets `error` to `err.message` directly, with no path to recover the original text.
- **Expected.** The sales-manager persona sees the specific reason their config was rejected (which band gapped, which weight is out of range, which signal type is missing) so they can self-correct — the entire point of shipping semantic validation (P0-2/P1-5/P1-6/P1-7) and a settings UI (P1-10) for a non-developer.
- **Actual.** Every scoring-config validation failure — band gap, band overlap, missing weight key, oversized weight, invalid band name — renders as "That link isn't valid — reset filters and try again." There is no link and nothing to reset on this page; the copy is not just unhelpful but actively confusing.
- **User impact.** This re-opens the practical effect of the original P1-10 gap: a non-technical operator who mistunes a band or forgets a weight key gets a message that doesn't apply to the screen they're looking at, and has no way to tell what to fix short of guessing or asking a developer — despite the backend now doing the hard work of telling them exactly what's wrong.
- **Test coverage gap:** `frontend/tests/scoring-settings.test.tsx` mocks `@/lib/api` entirely (`vi.mock`), so the real `request()` message-rewrite logic is never exercised against this page; the one save-failure-adjacent test present covers *load* failure only, using a hand-built `ApiRequestError` that bypasses the rewrite. This is the same "thin coverage on the paths that fail" pattern flagged as P3-27 last review — it is why this one wasn't caught.
- **Suggested Fix Location:** `frontend/lib/api.ts` (scope the generic-message substitution to the caller that needs it — e.g. have `fetchClinics`/`buildClinicListQuery`'s caller apply that specific copy, rather than rewriting inside the shared `request()` — or pass the original `message` through unmodified and let each page's catch block decide); regression test in `frontend/tests/scoring-settings.test.tsx` that exercises the real `request()` function (or an equivalent integration test) against a mocked `422 VALIDATION_ERROR` fetch response and asserts the specific band/weight message renders.

### NEW-2 · Scoring bands editor has no client-side contiguity check or boundary sync

- **Domain:** Input Validation / UX
- **Severity:** Medium
- **Priority:** P2
- **Summary:** `frontend/components/scoring-settings-client.tsx` renders each band's `min`/`max` as independent form state with no synchronization between adjacent bands, while the `CardDescription` above the form tells the user bands "must start at 0, be contiguous, and end unbounded."
- **Steps to reproduce (source-level, not DOM-observed):** Read `scoring-settings-client.tsx:154–185` — raising `COLD`'s `max` from 50 to 60 does not touch `WARM`'s `min` (still 51), so the two fields drift out of sync with no visual warning; the mismatch is only caught server-side on Save (and, per NEW-1, reported with an unhelpful message).
- **Expected.** Either the adjacent boundary auto-updates (e.g. `WARM.min` tracks `COLD.max + 1`), or an inline client-side warning appears as soon as a gap/overlap exists, before the user attempts to save.
- **Actual.** No feedback until the (currently broken, see NEW-1) server round-trip.
- **User impact.** Compounds NEW-1: the persona this page is built for has no way to self-correct proactively, and — until NEW-1 is fixed — no way to understand the failure reactively either.
- **Suggested Fix Location:** `frontend/components/scoring-settings-client.tsx` (band `onChange` handlers, or a derived-validity check rendered near the Save buttons).

## Positive Findings

- **SSRF guard held under fresh, adversarial probing.** Live-tested this pass against a cloud-metadata address (`169.254.169.254`), an internal container IP, and a `file://` URL — all three correctly rejected with `skipped=true` and a specific reason, no signals wiped, no crash.
- **CORS is correctly locked down.** A preflight from `https://evil.example` gets `400` with no `Access-Control-Allow-Origin` header.
- **Rate limiting resists the exact spoofing technique that broke it last cycle.** 8 requests with rotating forged `X-Forwarded-For` values all still hit `429` under an active limit.
- **XSS is safe by construction, not by luck.** `grep -r dangerouslySetInnerHTML` across the whole frontend returns nothing — every rendered field, including the deliberately hostile clinic name seeded for this pass (`<script>alert(1)</script> Clinic`), goes through JSX's default text-escaping with no bypass anywhere in the codebase.
- **Secret hygiene on this machine is better than a shallow file-permission check would suggest.** Both local `.env` files (`./.env`, `backend/.env`) are `600`, gitignored, untracked, and sit under a `700` parent directory (`/mnt/sda`) that blocks other local accounts from traversing to them at all — checked the full chain, not just the file mode.
- **The BFF proxy (`app/api/backend/[...path]/route.ts`) is carefully built:** path-traversal guard, scheme allowlist on the configured upstream, `redirect: "manual"` (never blindly follows a redirect with the operator key attached), and a minimal response-header allowlist rather than forwarding everything upstream sends back.
- **Test suite grew with the feature set, not just alongside it:** 68→87→88 backend tests and 6→15→17 frontend tests across the two review cycles, tracking real new surface area (scoring settings, rate-limit trust boundary) rather than churn.
