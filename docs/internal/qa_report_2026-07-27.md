# 1. Planning Review

## 1.1 Problem / product alignment

The stated problem — *"sales teams waste time on cold, manual prospecting; they lack a prioritized list of clinics showing buying intent"* — is coherent, narrow, and testable. The documentation set (`docs/context/product.md`, `architecture.md`, `roadmap.md`, `docs/tasks/phase-*.md`, `docs/standards/*`, `docs/runbooks/*`) is the strongest asset in this repository. It is unusually complete for an MVP: PRD, domain model, ERD with DDL, API catalog, folder structure, sprint plan with a critical-path diagram, deploy and rollback runbooks. Requirements are traceable from user story → phase → endpoint.

The **core loop is implemented end to end** and works: discover → detect signals → score → enrich → ranked dashboard → clinic detail with evidence. A rep can filter to Hot and open a clinic to see why it ranks. That is the MVP demo definition from `roadmap.md`, and it holds up.

## 1.2 Requirements satisfied vs. claimed

`product.md` line 21 and `roadmap.md` line 748 both assert **"MVP (Phases 1–7) complete."** That claim is too strong. Specific gaps:

| PRD requirement | Status | Note |
|---|---|---|
| §5.1 collect **social media URLs** | ❌ Not implemented | `google_places.py:95` hardcodes `social_urls=[]`; never populated, never rendered |
| §5.2 profile stores **services offered** | ❌ Removed | migration `0003_drop_clinic_services` dropped the column; detail page shows no services |
| §5.6 dashboard **sort** | ⚠️ API only | `sort` is supported by `GET /clinics` but no UI control exists, and `FilterBar` hardcodes `sort: "-score"` on every apply — `sort=name` is unreachable from the product |
| §6 "Auth beyond a single admin/operator role + API key" is out of scope | ❌ | The exclusion implies *one* operator role + API key **is** in scope. Nothing is implemented. `app_user` table and `JWT_SECRET` exist as dead scaffolding; `POST /auth/login` is marked "Planned" |
| US-D2 tune weights **"without a developer"** | ❌ | Only reachable by hand-crafting a `PUT /scoring-config` JSON body with `curl`. No admin UI. This is the sales-manager persona's only feature and it is developer-only in practice |
| US-C2 "re-running **replaces prior signals of the same type**" | ❌ Contradicted | Implementation deletes *all* signals for the clinic — see **P0-1** |
| Success metric: dashboard < 2s for 1k clinics | ✅ Verified | 27–43 ms at 1,060 clinics |
| Success metric: weights tunable without redeploy | ⚠️ Partial | Config *is* DB-backed and hot, but silently ineffective in a common case — see **P1-6** |

## 1.3 User journey completeness

The **rep journey** (search → filter → open → read breakdown) is logical and complete.

The **operator journey is missing from the product.** Every write action — discovery, detection, scoring, enrichment, config tuning — exists only as a CLI command or a raw HTTP call. There is no page, button, or form anywhere in the frontend that mutates data. Consequences a reviewer should weigh:

- The "Growth Probability" column — one of the five columns the PRD mandates — renders `—` for every clinic until someone SSHes in and runs `python cli.py enrich --all`. In the seeded environment this was visible immediately.
- A rep who notices a clinic's data is stale has no way to refresh it.
- The frontend exports `fetchScoringConfig()` (`lib/api.ts:101`) and defines the full `ScoringConfig` type, but nothing imports either. This is the vestige of a planned admin screen that was never built.

## 1.4 Assumptions, ambiguities, missing requirements

1. **Signal detection reads only the homepage.** `WebsiteCrawler.fetch(url)` retrieves one page. Hiring signals live on `/careers`; locations live on `/locations`. The detector compensates by matching link *text/href* ("careers", "jobs", "location"), which is a proxy, not evidence. Expect low recall and unverifiable evidence strings. No requirement states crawl depth.
2. **Detection heuristics are hardcoded English + US-centric**, while the pilot region in every example is Lisbon. `HIGH_TICKET_KEYWORDS` has no Portuguese terms (`implantes`, `facetas`, `alinhadores`); `_estimate_locations_count` counts US ZIP patterns `\b\d{5}(-\d{4})?\b` — a Portuguese postal code is `1000-001`, which matches partially and by accident. The keyword lists are code constants, not config, so they cannot be tuned without a redeploy — inconsistent with the "config-driven scoring" principle applied one layer up.
3. **No definition of score staleness.** Nothing records when a clinic was last crawled at the clinic level, no re-crawl cadence is specified, and the detail page never displays signal age (see **P2-14**). A rep cannot distinguish a signal detected today from one detected six months ago.
4. **`confidence` is captured but never used.** It is stored, returned, and displayed, but plays no part in scoring. Either it should weight the contribution or it is decoration.
5. **AI enrichment's role is undefined.** The UI calls it "advisory… they augment, not override, rule-based scoring," but the PRD §5.4 says the score is a "sum of weights… plus optional AI contribution." AI contributes nothing to the score in the implementation. The docs and the product disagree.

## 1.5 Prioritization judgment

Sequencing (foundation → discovery → signals → scoring → AI → dashboard → deploy) is correct: value-bearing slices first, AI parallelized off the critical path. The one misjudgment is that **Phase 5 (AI enrichment) shipped before authentication and before any operator UI.** AI enrichment is the most expensive feature per call and the least essential to the core promise, and it shipped on an endpoint anyone on the network can invoke in a loop.

# 2. Development Review

## 2.1 What is done well

- **Clean Architecture is genuinely applied, not just named.** Domain imports nothing outward; ports are real Protocols; use cases are thin and testable; infrastructure implements the ports. The dependency rule holds under inspection.
- **The SSRF guard (`website_crawler.py`) is the best code in the repo.** Scheme allowlist, DNS resolution checked against private/loopback/link-local/reserved/multicast, manual redirect following with per-hop revalidation, and — the part most implementations miss — the resolved IP is *pinned* into the request URL with `Host` and SNI preserved, closing the DNS-rebind window between check and connect. Correct.
- **Secret handling in the AI layer.** Provider keys go in headers, never query strings. `EnrichmentFailedError` deliberately logs the raw upstream body server-side and returns a generic message to the client (`main.py:52-68`) — verified live: a real Gemini `UNAUTHENTICATED` body appeared in the server log and *not* in the 502 response.
- **Enrichment input fingerprinting** (`compute_input_fingerprint`) skips re-billing the LLM when nothing changed. Real cost discipline.
- **Concurrency handling on `PUT /scoring-config`**: `SELECT … FOR UPDATE` on the active row plus `IntegrityError` → 409, with a partial unique index enforcing one active config. Thought through.
- Docker images are multi-stage, run as non-root, and carry healthchecks. CI runs lint + format + migrations + tests on both stacks.

## 2.2 Implementation problems

- **No validation layer between "syntactically valid JSON" and "semantically valid scoring config."** `UpdateScoringConfigRequest` checks only that weights are non-negative and bands are non-empty. It does not check band names against `PriorityLevel`, band coverage, band overlap, weight keys against `SignalType`, or integer bounds. Four separate defects flow from this single omission (P0-2, P1-5, P1-6, P1-7).
- **Failure is modeled as "no data" rather than "no information."** `DetectSignals` responds to a crawl failure by writing an empty signal set (`detect_signals.py:44` and `:55`). Absence of evidence is persisted as evidence of absence. This is the root of the most damaging bug in the product.
- **`RescoreAll` is an N+1 loop with per-iteration commits.** For each clinic it calls `get_detail` (which eagerly loads locations, signals, score *and* enrichment purely to check existence), then `list_by_clinic`, then `get_by_clinic`, then commits. No batching, no single transaction, executed inline in the request thread.
- **Duplicate join logic.** `sqlalchemy_clinic_repo.py:146-177` guards the `LocationModel` join with `joined_location` three times; the first block already makes the two later branches unreachable. Harmless but confusing dead logic.
- **Dead code:** `getApiBaseUrl()`'s server branch (`lib/api.ts:24-28`) can never execute because no server component fetches; `fetchScoringConfig`; `FilterBar`'s `onChange` prop; the `app_user` table; `JWT_SECRET`.
- **`ScoringConfigResponse.bands` reuses `ScoreBandSchema`**, whose `model_validator` runs on *responses* too. A config stored with `max < min` would make `GET /scoring-config` throw a 500 rather than report the bad state — the endpoint you would use to diagnose it.

## 2.3 UI / interaction review

Visual language is consistent: one HSL token set in `globals.css`, shadcn-style primitives, uniform card/badge/table treatment, consistent 4/6-unit spacing, one font (Inter), one icon family (lucide). Priority colors follow a sensible cold→immediate temperature ramp and are reused identically in `ScoreBadge`, `PriorityTag`, and `ScoreBreakdown`. Empty states exist and are well-written on all four surfaces (no results, no score, no enrichment, no signals). Loading states exist on both pages. Nothing is visually broken.

The weaknesses are interaction-level, not cosmetic:

- The header contains no navigation and the product name is not a link. Every page-to-page move relies on one "Back to list" button or the browser.
- **"Back to list" navigates to bare `/clinics`, discarding all filters and the page number** (`clinic-detail-view.tsx:94`). The core rep workflow is *filter → open → back → open next*; this breaks it every single time.
- Column headers are inert text. Users trained on every other data table will click "Score" and get nothing.
- `"Sorted by score (high to low)"` is a hardcoded string, rendered regardless of the actual `sort` parameter.
- Filters require an explicit "Apply" click. Defensible, but four of the six controls are `Select` dropdowns where users expect immediate effect.
- No confirmation dialogs and no success toasts anywhere — because the UI contains no mutating actions at all.

# 3. Detailed Findings

Each finding is reproducible against a stock `docker compose up` environment. `{id}` is any seeded clinic UUID; `$B = http://localhost:8000/api/v1`.

### P0-1 · Signal detection erases all stored signals when a site is unreachable, collapsing the clinic's score to 0/COLD

**Category:** Data integrity / Core business logic
**Severity:** Critical · **Priority:** P0

**Description.** `DetectSignals.execute` calls `signal_repo.replace_for_clinic(clinic_id, [])` on both failure paths — crawl error (`detect_signals.py:55`) and missing website (`:44`). `replace_for_clinic` issues an unconditional `DELETE … WHERE clinic_id = ?` before inserting (`sqlalchemy_signal_repo.py:30`). A transient DNS blip, an expired TLS cert, a 503, or a slow site exceeding the 10 s timeout therefore **permanently destroys every previously detected signal** for that clinic. The next scoring run reads zero signals and writes `total=0, priority=COLD`.

This also directly contradicts the documented contract in `docs/standards/api_rules.md` ("Signal detection replaces same-type signals per clinic") and the acceptance criterion for US-C2.

**Steps to reproduce.**
1. Seed a clinic with 5 detected signals; score it. Verify `GET $B/clinics/{id}` → `"total": 130, "priority": "HOT"`.
2. Point the clinic's `website` at an unreachable host (or disconnect egress).
3. `POST $B/clinics/{id}/signals:detect`
4. `GET $B/clinics/{id}/signals`
5. `POST $B/clinics/{id}/score`

**Expected.** Prior signals are retained; the run reports the failure and leaves the score untouched.

**Actual (verified live).**
```
POST …/signals:detect  → 202 {"detected":0,"signals":[],"skipped":true,
                              "skip_reason":"Failed to fetch https://example38.test:
                               DNS resolution failed: [Errno -2] Name or service not known"}
GET  …/signals         → 200 {"data":[]}
POST …/score           → 202 {"total":0,"priority":"COLD","breakdown":{}}
```
The clinic went from **HOT/130 to COLD/0** on a DNS failure, with no error surfaced to any user.

**User impact.** Severe and silent. `cli.py detect --all` is the documented batch command; running it during any partial network incident, behind a proxy outage, or against a set of clinics whose sites are seasonally down will wipe those clinics from the top of the call list. The reps never see an error — the clinics simply stop appearing in the Hot filter. This defeats the product's single purpose ("which clinics should I contact first?") and the damage is invisible and cumulative. There is no crawl-status field, so it is not even diagnosable after the fact.

**Recommendation.**
1. On any `WebsiteFetchError` or missing website, **do not write.** Return `skipped=True` and leave existing signals in place.
2. Persist crawl outcome per clinic (`last_crawl_at`, `last_crawl_status`, `last_crawl_error`) so staleness is visible and re-crawls can be targeted.
3. Change `replace_for_clinic` to a per-type upsert to match the documented and specified behaviour (`uq_signal_clinic_type` already exists to support this).
4. Add regression tests for both failure paths — the existing suite covers the happy path only.

### P0-2 · A valid-looking scoring-config edit permanently bricks the scoring engine, with no in-product recovery

**Category:** Availability / Input validation
**Severity:** Critical · **Priority:** P0

**Description.** `ScoreBandSchema.name` is an unconstrained `str`. `ScoringService.compute` then does `PriorityLevel(config.priority_for_total(total))` (`scoring_service.py:24`), which raises `ValueError` for any name outside `COLD|WARM|HOT|IMMEDIATE`. The config write commits *before* the rescore runs, so the bad config becomes the active version and **every subsequent scoring call raises 500** — forever, until someone edits the database or issues another correct `curl`. US-D2 explicitly targets a non-developer for this feature.

**Steps to reproduce.**
```bash
curl -X PUT $B/scoring-config -H 'Content-Type: application/json' -d '{
  "weights":{"HIRING":25,"ADVERTISING":30,"WEBSITE_QUALITY":15,
             "MULTI_LOCATION":40,"HIGH_TICKET":20},
  "bands":[{"name":"SUPER_HOT","min":0,"max":null}]}'
curl -X POST $B/clinics/{id}/score
```

**Expected.** 422 rejecting the unknown band name, active config unchanged.

**Actual (verified live).**
```
PUT  /scoring-config          → 200 {"version":7,"bands":[{"name":"SUPER_HOT",…}]}
POST /clinics/{id}/score      → 500 Internal Server Error   (plain text, no error envelope)
```
With `"rescore": true` the `PUT` itself returns `500` — **and the broken config is still committed and active** (verified: `GET /scoring-config` afterwards returned the bad `version: 9`). Reads keep working, so the dashboard continues serving pre-existing scores as if nothing is wrong.

**User impact.** A sales manager tuning bands — the exact intended use — can take the scoring engine offline with one request and no way to undo it from any product surface. Because the dashboard still renders stale scores, the failure is invisible until someone notices rankings have frozen.

**Recommendation.** Constrain `ScoreBandSchema.name` to the `PriorityLevel` enum (`Literal["COLD","WARM","HOT","IMMEDIATE"]`). Validate the config *and* run the rescore inside one transaction so a failure rolls the config back. Add a `POST /scoring-config/validate` dry-run, and keep prior versions restorable (the versioned table already supports this — expose it).

### P1-3 · Every mutating and paid endpoint is unauthenticated and unthrottled; OpenAPI docs are public

**Category:** Security / Cost
**Severity:** High · **Priority:** P1

**Description.** No auth exists on any route. `POST /clinics/discover` (billed Google Places), `POST /clinics/{id}/enrich` (billed LLM), `POST /clinics/{id}/signals:detect` (outbound crawl), and `PUT /scoring-config` (business logic) are all open. `/docs` and `/openapi.json` return 200, publishing the entire surface. 30 rapid unauthenticated requests all returned 200 — no rate limiting at any layer.

The team documents this honestly in `architecture.md:736` and `api_rules.md` and prescribes network isolation as the mitigation. That is a legitimate interim control, but `docker-compose.prod.yml` publishes `${API_PORT:-8000}:8000` on all interfaces by default, so the documented mitigation is not the default configuration.

**Steps to reproduce.** From any host that can reach the API: `curl -X POST $B/clinics/discover -H 'Content-Type: application/json' -d '{"query":"dentist"}'` in a loop. Each call costs up to `PLACES_MAX_PAGES × 20` billed Places results. Same for `/enrich` against the LLM.

**Expected.** 401 without credentials.

**Actual.** Request executes; only `PLACES_MAX_PAGES` (per call, not per period) bounds spend.

**User impact.** Direct financial exposure — an unbounded loop against `/discover` or `/enrich` converts to a third-party invoice. Anyone reaching the API can also rewrite scoring weights and re-rank the entire sales pipeline.

**Recommendation.** Ship the single-operator API key the PRD already scopes in (`X-API-Key` dependency on all non-GET routes is a few hours of work) before any non-isolated deployment. Add per-IP rate limits on the four expensive routes. Disable `/docs` and `/openapi.json` when `APP_ENV=production`. Change the prod compose default to bind `127.0.0.1:${API_PORT}:8000`.

### P1-4 · `POST /clinics/discover` returns a bare `500 Internal Server Error` when the Places key is missing or the upstream fails

**Category:** Error handling / API contract
**Severity:** High · **Priority:** P1

**Description.** `GooglePlacesClient.search` raises `ValueError("GOOGLE_PLACES_API_KEY is not configured")` (`google_places.py:43`) with no handler registered. The same gap swallows every upstream `httpx.HTTPStatusError` — quota exhaustion (429), invalid key (403), Places outage (5xx) all become an opaque 500 with no error envelope, violating the contract in `api_rules.md` ("Server error → 500 (no stack trace in body)" and the mandatory `{"error":{...}}` envelope).

**Steps to reproduce.** With `GOOGLE_PLACES_API_KEY` empty (the shipped default in `.env.example`):
`curl -X POST $B/clinics/discover -H 'Content-Type: application/json' -d '{"query":"dentist in Lisbon"}'`

**Expected.** `503` or `422` with `{"error":{"code":"DISCOVERY_UNAVAILABLE","message":"Google Places API key is not configured"}}`.

**Actual (verified live).** `HTTP 500`, body `Internal Server Error` (plain text), full traceback in server logs.

**User impact.** This is the very first command a new operator runs after `docker compose up`, and the shipped default configuration guarantees it fails opaquely. It is also the worst possible failure mode for quota exhaustion during a large ingest — the operator cannot distinguish "key missing" from "quota gone" from "Places is down."

**Recommendation.** Add `ClinicSourceError` / `ClinicSourceUnavailableError` domain exceptions with handlers in `create_app()`, mirroring the existing `EnrichmentFailedError` pattern (which is done correctly). Add a catch-all `Exception` handler that emits the envelope with a request ID and no internals.

### P1-5 · Band gaps are accepted; scores falling in a gap are mislabelled with the last band's priority

**Category:** Correctness / Validation
**Severity:** High · **Priority:** P1

**Description.** `ScoringConfig.priority_for_total` falls through to `self.bands[-1].name` when no band matches (`scoring_config.py:22`). Nothing validates that bands tile `[0, ∞)`.

**Steps to reproduce.**
```bash
curl -X PUT $B/scoring-config -H 'Content-Type: application/json' -d '{
  "weights":{"HIRING":10,"ADVERTISING":10,"WEBSITE_QUALITY":10,
             "MULTI_LOCATION":0,"HIGH_TICKET":0},
  "bands":[{"name":"COLD","min":0,"max":10},{"name":"HOT","min":50,"max":null}],
  "rescore":true}'
curl -X POST $B/clinics/{id}/score
```

**Expected.** 422 — bands leave 11–49 uncovered.

**Actual (verified live).** `200 {"version":6,…,"rescored":60}`, then
`{"total":30,"priority":"HOT",…}` — **a score of 30 labelled HOT** under a config whose HOT band starts at 50.

**User impact.** Reps prioritize by the priority tag, not the raw number. Mislabelling makes the ranked call list actively wrong while looking perfectly normal, and it silently propagated to all 60 clinics in the rescore. Overlapping bands are likewise accepted, making the result order-dependent on JSON array position.

**Recommendation.** Validate on write that bands are sorted, contiguous, non-overlapping, start at 0, and end unbounded. Reject anything else with a 422 naming the gap. Make `priority_for_total` raise instead of silently falling through.

### P1-6 · Omitting a weight key silently falls back to the stale stored weight — the config edit reports success but changes nothing

**Category:** Correctness / Config
**Severity:** High · **Priority:** P1

**Description.** `ScoreBreakdown.from_signals` does `weights.get(signal_type, signal.applied_weight)` (`score_breakdown.py:20`). When a key is absent from the active config it silently reuses the weight frozen into the `signal` row at detection time. So a config edit that removes or renames a weight is a no-op that reports success.

**Steps to reproduce.**
```bash
curl -X PUT $B/scoring-config -H 'Content-Type: application/json' \
     -d '{"weights":{},"bands":[{"name":"COLD","min":0,"max":10},{"name":"HOT","min":50,"max":null}]}'
curl -X POST $B/clinics/{id}/score
```

**Expected.** Either a 422 (weights must cover all `SignalType` values) or a score of 0.

**Actual (verified live).** `PUT` → `200 {"version":2,"weights":{}}`. Score → `{"total":130,"breakdown":{"ADVERTISING":30,"HIGH_TICKET":20,"HIRING":25,"MULTI_LOCATION":40,"WEBSITE_QUALITY":15}}` — **the full old weights, from a config that contains none of them.**

**User impact.** Breaks the central promise of US-D2 ("editing config recomputes scores; no redeploy"). A manager who zeroes out a signal sees a success response and an unchanged ranking, with no way to tell which value is actually in force. It also means signal weights are effectively frozen at detection time, so *changing* a weight only takes effect for clinics re-detected afterwards unless every key is supplied.

**Recommendation.** Require the weights map to contain every `SignalType` key on write (422 otherwise). Make `from_signals` default to `0` for unknown keys, never to `signal.applied_weight`. Consider dropping `signal.applied_weight` from the read path entirely so config is the single source of truth.

### P1-7 · Out-of-range weights are accepted and crash every scoring call with a 500

**Category:** Validation / Availability
**Severity:** High · **Priority:** P1

**Description.** `weights` is `dict[str, int]` with only a `>= 0` check. `score.total` is a Postgres `INTEGER`. A weight above 2³¹−1, or a combination that overflows in aggregate, is stored happily in the JSONB config and then fails on insert.

**Steps to reproduce.**
```bash
curl -X PUT $B/scoring-config -H 'Content-Type: application/json' -d '{
  "weights":{"HIRING":3000000000,"ADVERTISING":30,"WEBSITE_QUALITY":15,
             "MULTI_LOCATION":40,"HIGH_TICKET":20},
  "bands":[{"name":"COLD","min":0,"max":null}]}'
curl -X POST $B/clinics/{id}/score
```

**Expected.** 422 with a stated upper bound.

**Actual (verified live).** `PUT` → `200 {"version":8,…}`; `POST …/score` → `500 Internal Server Error`. `{"weights":{"HIRING":99999999999999999999}}` is likewise accepted.

**User impact.** A fat-fingered extra digit takes scoring down for the whole dataset, with the same no-recovery-path problem as P0-2.

**Recommendation.** Bound weights (e.g. `Field(ge=0, le=1000)`) and band `min`/`max` to sane integer ranges in the Pydantic schema.

### P1-8 · `rescore=true` runs synchronously in the request thread — 27.7 s at 1,060 clinics, with partial commits on failure

**Category:** Performance / Reliability
**Severity:** High · **Priority:** P1

**Description.** `UpdateScoringConfig` calls `RescoreAll.execute()` inline. That is an N+1 loop with a `get_detail` (four eager relationship loads) plus two more queries and an individual `COMMIT` per clinic. There is no job queue — `architecture.md` states background work runs as cron-invoked CLI, but this path runs in HTTP.

**Steps to reproduce.** Seed 1,060 clinics, then time `PUT $B/scoring-config` with `"rescore": true`.

**Expected.** Immediate `202` with a job handle, or a bounded synchronous operation.

**Actual (verified live).**

| Dataset | Wall clock |
|---|---|
| 60 clinics | 1.88 s |
| 1,060 clinics | **27.69 s** |

Linear at ~26 ms/clinic → ~13 s at the PRD's 500-clinic pilot target, ~2 min 10 s at 5,000. Most reverse proxies and load balancers default to a 30–60 s timeout. Because each clinic commits separately, a mid-loop failure (see P0-2, P1-7) leaves the dataset **partially rescored** across two config versions with no rollback.

**User impact.** At pilot scale the manager waits half a minute staring at a spinner-less `curl`; past ~1,200 clinics the request starts timing out while the work continues server-side, so the caller cannot tell whether it succeeded. Mixed-version score data corrupts the ranking.

**Recommendation.** Return `202` with a job id and run the rescore out of band (the CLI already exists — invoke that path). Failing that: batch the loop into one transaction, replace `get_detail` with an existence check, and load all signals in a single grouped query.

### P1-9 · The dashboard's API URL is baked in at image build time and defaults to `localhost` in the production compose file

**Category:** Deployment / Configuration
**Severity:** High · **Priority:** P1

**Description.** Every data fetch happens in a `"use client"` component, so `getApiBaseUrl()` always takes the browser branch and reads `NEXT_PUBLIC_API_URL` — a value inlined at `next build` time (`Dockerfile:10-11`). The server branch reading `API_URL` (`lib/api.ts:24-28`) is unreachable dead code, yet `docker-compose.prod.yml` sets `API_URL: http://api:8000/api/v1`, which strongly implies a server-side fetch that never occurs. Worse, the same file defaults `NEXT_PUBLIC_API_URL` to `http://localhost:8000/api/v1`.

**Steps to reproduce.** Deploy `docker-compose.prod.yml` to a remote host without overriding `NEXT_PUBLIC_API_URL`; open the dashboard from a laptop.

**Expected.** The dashboard calls the deployed API.

**Actual.** The browser calls `http://localhost:8000/api/v1` — *the viewer's own machine*. Every request fails; the user sees "Failed to fetch clinics." A GHCR image built by `deploy.yml` also carries whatever URL was set at build time, so one image cannot serve staging and production.

**User impact.** A first production deploy that follows the documented runbook produces a completely non-functional dashboard, and the misleading `API_URL` variable sends the operator debugging in the wrong direction.

**Recommendation.** Move list/detail fetching into Server Components (which also fixes the SSR gap) so `API_URL` becomes real and runtime-configurable, or expose the base URL through a runtime-injected config endpoint. ### P2-12 · Invalid filter values return empty results instead of a validation error

**Category:** Input validation / UX
**Severity:** Medium · **Priority:** P2

**Description.** `priority`, `signal_type`, and `sort` are unconstrained strings. Unknown values match nothing (or silently fall back).
**Actual (verified live).**

### P2-13 · A malformed URL parameter shows a raw Pydantic error plus a misleading recovery hint

**Category:** Error handling / UX
**Severity:** Medium · **Priority:** P2

**Description.** `buildClinicListQuery` does `Number(searchParams.get("page") ?? "1")` with no `isNaN` guard, so `?page=abc` sends `page=NaN` to the API.
**Steps to reproduce.** Open `/clinics?page=abc` (a truncated bookmark or hand-edited URL).
**Actual (verified live).** API returns `422 {"detail":[{"loc":["query","page"],"msg":"Input should be a valid integer, unable to parse string as an integer"}]}`. The dashboard renders a red panel reading *"page: Input should be a valid integer…"* above *"Check that the API is running and `NEXT_PUBLIC_API_URL` is configured."*
**Expected.** Coerce invalid numerics to defaults; on genuine errors show a message appropriate to the audience.
**User impact.** A sales rep is shown a Pydantic stack message and told to check an environment variable. The hardcoded hint is wrong for every non-network error and leaks internal configuration names into the product.
**Recommendation.** Guard all `Number()` conversions with `Number.isFinite`. Branch the error copy on status: network → "Can't reach the service"; 4xx → "That link isn't valid — reset filters"; 5xx → "Something went wrong, try again." Add a "Reset filters" button in the error state.

**Severity:** Medium · **Priority:** P2

### P2-15 · List ordering does a sequential scan with a per-row correlated subquery; `ix_score_total` is never used

**Category:** Performance / Scalability
**Severity:** Medium · **Priority:** P2

**Description.** Sorting and score filtering use correlated scalar subqueries against `score` (`sqlalchemy_clinic_repo.py:179-199`), so Postgres cannot use the `total DESC` index and must evaluate the subquery for every clinic before applying `LIMIT`. The count query wraps the same statement in another full pass.

**Actual (`EXPLAIN ANALYZE`, 1,060 clinics, page 1 of 20):**
```
Limit (actual time=28.100..28.345 rows=20)
  -> Sort  Sort Key: ((SubPlan 1)) DESC NULLS LAST   Method: top-N heapsort
     -> Seq Scan on clinic (rows=1060)
          SubPlan 1 -> Index Scan using score_clinic_id_key on score (loops=1060)
Execution Time: 28.544 ms
```
**Current state.** The PRD target (< 2 s for 1k clinics) is comfortably met — end-to-end HTTP was **27–43 ms**. This is a scalability finding, not a present defect.
**User impact.** Cost is O(N) per page regardless of page number, so it degrades linearly: roughly 2.5–3 s per page at 100k clinics, doubled by the count query. Also, `q` uses `ILIKE '%…%'`, which no btree index can serve.
**Recommendation.** `LEFT OUTER JOIN score` and `LEFT OUTER JOIN enrichment` instead of correlated subqueries so `ix_score_total` becomes usable; add `pg_trgm` GIN indexes on `clinic.name` and `location.city` before search volume grows; consider an approximate or cached count.

### P2-18 · The search box treats `%` and `_` as SQL wildcards

**Category:** Input handling
**Severity:** Medium · **Priority:** P2

**Description.** `pattern = f"%{query.q}%"` is passed to `ilike` without escaping LIKE metacharacters (`sqlalchemy_clinic_repo.py:154`).

### P2-19 · Detection heuristics are hardcoded, English-only, and homepage-only

**Category:** Core logic quality
**Severity:** Medium · **Priority:** P2

**Description.** All five detectors match hardcoded English substrings against a single fetched page. `_estimate_locations_count` counts US ZIP patterns (`\b\d{5}(-\d{4})?\b`). The pilot region in every document and example is Lisbon.
**User impact.** For a Portuguese pilot, `HIGH_TICKET` will miss `implantes`/`facetas`/`alinhadores`, `HIRING` will miss `recrutamento`/`carreiras`, and the location estimator will match Portuguese postal codes (`1000-001`) by coincidence rather than design. **Recommendation.** Move keyword lists into the scoring config (they are business rules, not code) or at minimum a locale-keyed YAML; crawl `/careers`, `/locations`, and `/services` when linked; make the address regex locale-aware.

# 7. Release Recommendation

## Is this MVP ready for production?

# ❌ No

## Technical justification

The product is closer to ready than the verdict suggests — the architecture is sound, the documentation is exemplary, the read path is fast, the test suite is green, and the core rep workflow works exactly as specified. The blocking issues are few and localized. But three of them are disqualifying for a production release, and none is a matter of polish:

**1. The system silently destroys the data it exists to produce (P0-1).** A transient DNS failure, TLS expiry, or 10-second timeout during `cli.py detect --all` permanently deletes a clinic's signals and drops it from HOT to COLD on the next scoring run — verified live. No error reaches any user, no crawl status is recorded, and the damage accumulates every batch run. For a product whose entire value is "which clinics should I call first," a failure mode that quietly removes the best prospects from the top of the list is worse than an outage: an outage is noticed. This alone prevents release.

**2. The scoring engine can be permanently disabled by its intended user with valid-looking input (P0-2).** A band name outside the four-value enum is accepted, committed as the active config, and then throws on every scoring call thereafter. There is no admin UI to fix it, no rollback endpoint, and no version restore — recovery requires direct database access. US-D2 explicitly designates a non-developer as the person who edits this config. Combined with P1-5 (band gaps mislabel scores), P1-6 (omitted weights silently do nothing), and P1-7 (unbounded weights crash scoring), the config surface has essentially no semantic validation, and it is the one surface the PRD hands to a non-technical user.

**3. Expensive third-party endpoints are open to the network (P1-3).** `POST /clinics/discover` (billed Google Places), `POST /clinics/{id}/enrich` (billed LLM), and `PUT /scoring-config` require no credentials and are not rate limited; `/docs` publishes them. The team documents this and prescribes network isolation, which is a legitimate interim control — but `docker-compose.prod.yml` publishes port 8000 on all interfaces by default, so the shipped configuration does not implement the documented mitigation. Anyone who reaches the API can generate an unbounded third-party bill or re-rank the entire pipeline.

Supporting this verdict: the production compose file's default `NEXT_PUBLIC_API_URL` points the deployed dashboard at the *viewer's* localhost (P1-9), meaning a first deploy following the documented runbook yields a completely non-functional UI; and the rescore path blocks an HTTP request for 27.7 seconds at 1,060 clinics, exceeding common proxy timeouts at the scale the PRD targets (P1-8).

## Path to release

This is roughly **one to two engineer-weeks**, and the fixes are concentrated in a handful of files:

| Gate | Work | Files |
|---|---|---|
| **Required for "Yes, with reservations"** | Stop writing empty signal sets on failure; persist crawl status; per-type upsert | `detect_signals.py`, `sqlalchemy_signal_repo.py` |
| | Constrain band names to `PriorityLevel`; validate band coverage/overlap; bound weights; require full weight coverage; wrap config update + rescore in one transaction | `schemas/scoring_config.py`, `score_breakdown.py`, `compute_score.py` |
| | Single-operator API key on all non-GET routes; rate limit the four expensive endpoints; disable `/docs` when `APP_ENV=production`; bind prod API to `127.0.0.1` | `deps.py`, `main.py`, `docker-compose.prod.yml` |
| | Handle `ClinicSourceError` + a catch-all with the documented error envelope | `main.py`, `google_places.py` |
| | Fix the production `NEXT_PUBLIC_API_URL` default; remove or wire up `API_URL` | `docker-compose.prod.yml`, `lib/api.ts` |
| | Regression tests for every item above | `tests/api/`, `tests/unit/` |
| **Required for "Yes"** | Move rescore off the request path | `compute_score.py`, `scoring_config.py` |
| | Minimal `/settings/scoring` admin page + per-clinic re-run buttons (closes US-D2) | new frontend routes |
| | Preserve filters in back-navigation; `aria-live` on the results region | `clinic-detail-view.tsx`, `clinics-page-client.tsx` |

With the first block done, this is a credible internal pilot behind a VPN. With both blocks, it is a defensible production MVP.

# 8. QA Persona Notes

**First-time user.** Lands on `/` → redirects to `/clinics` → sees a ranked table immediately. Good. Then: Growth Probability is `—` for every row (nothing has been enriched), there is no explanation of what "Score 130" means, no legend for the priority bands, and no visible way to add clinics. The product looks broken on first contact even when it is working correctly.

**Experienced rep.** The daily loop — filter to Hot, work down the list — is directly supported and fast. The loop breaks on every back-navigation (P2-11). No way to mark a clinic contacted, no export, no sort by growth probability. Reps will paste this into a spreadsheet by day three.

**Distracted user.** Fills six filters, forgets to click "Apply," sees stale results with no indication that the form is dirty. Nothing warns them.

**Power user.** Discovers the API through the public `/docs`, drives everything from `curl`, and is the only persona currently well served — which is itself the finding.

**Malicious user.** Cannot inject SQL: every filter is parameter-bound and `' OR 1=1--`, `'; DROP TABLE clinic;--` in `q`, `state`, and `sort` all returned clean, correct results (verified). Cannot XSS: a stored `<script>alert(1)</script>` clinic name renders escaped through React, and the detail page validates `website` protocols before rendering an `href`. Cannot SSRF the crawler: scheme allowlist, IP denylist, per-hop redirect revalidation, and IP pinning are all correct. Cannot forge CORS: an `Origin: https://evil.example` preflight was rejected with 400 and no `Access-Control-Allow-Origin`. **Can** run up an unbounded Google Places and LLM bill, rewrite the scoring config, and take the scoring engine offline — all unauthenticated.

**Mobile user.** Layout adapts, the table scrolls horizontally in its own container, and the page never scrolls sideways. Five columns on a 375 px screen means near-constant horizontal scrolling; a stacked card list below `md` would serve this persona far better. Tap targets meet 44 px.

**Accessibility user.** Keyboard navigation reaches every control with visible focus rings; all form controls are labelled; contrast passes AA throughout; priority is never conveyed by color alone. But applying a filter announces nothing, errors announce nothing, the heading outline skips a level, and there is no skip link — so the experience is navigable but not comprehensible without sight.

## 9.3 Defect introduced by the P1-3 fix — rate-limiter bypass

The new `RateLimitMiddleware` correctly returned 429 after 30 requests, but the limit could be reset at will.

**Root cause was one layer above the middleware.** uvicorn ships `proxy_headers=True` by default (verified: uvicorn 0.49.0), and the remediation set `--forwarded-allow-ips=127.0.0.1`. When a request arrives from a trusted address, uvicorn **rewrites `scope["client"]` from `X-Forwarded-For` before any application code runs**. In the intended production topology the API binds to loopback behind a same-host reverse proxy, so *every* request arrives from `127.0.0.1` and is therefore trusted — meaning any caller could forge their own source address by setting one header.

Reproduced against the running API (`PUT /scoring-config`, limit 30/min, chosen because it fails validation fast and involves no DNS):

```
36 plain requests   : ..............................XXXXXX   (first 429 at #31)
8 with rotating XFF : [422, 422, 422, 422, 422, 422, 422, 422]   ← limit defeated
```

Consequences: the cost control protecting the billed `/discover` (Google Places) and `/enrich` (LLM) endpoints did not hold, and because buckets were keyed on a spoofable value that was never evicted, distinct forged addresses grew the in-memory map without bound.

*Methodological note:* an earlier attempt to demonstrate this against `/clinics/{id}/signals:detect` was **confounded** — each call performs a real DNS lookup, so 34 requests took longer than the 60 s window and the limit reset on its own rather than being bypassed. The finding was only confirmed after re-testing on a fast endpoint inside a single window, and independently by unit-testing the pre-fix `_client_key` in isolation.

### Remediation applied

1. **`backend/app/presentation/middleware/rate_limit.py`** — `X-Forwarded-For` is consulted only when the immediate peer is in an explicitly configured `RATE_LIMIT_TRUSTED_PROXIES` list (default: empty, trust nobody). The chain is walked right-to-left so the first address no trusted proxy vouched for wins, since leftmost entries are the forgeable ones. Bucket storage is now bounded: idle buckets are pruned once per window and a hard `max_tracked_keys` cap evicts least-recently-used entries.
2. **`backend/scripts/docker-entrypoint.sh`** — `FORWARDED_ALLOW_IPS` now defaults to **empty** (uvicorn trusts nobody, so `request.client` stays the real peer). Comments state that a value here makes uvicorn rewrite the peer address, that it must name only a proxy under your control, and that the proxy must **overwrite** `X-Forwarded-For` (`proxy_set_header X-Forwarded-For $remote_addr`) rather than append to a client-supplied value.
3. **`docker-compose.yml` / `docker-compose.prod.yml` / `.env.example` / `.env.production.example`** — `RATE_LIMIT_TRUSTED_PROXIES` wired through; `FORWARDED_ALLOW_IPS` default changed to empty, both documented as governing the same trust decision and needing to stay in sync.

Verified after remediation, same probe, same window:

```
36 plain requests   : ..............................XXXXXX   (first 429 at #31)
8 with rotating XFF : [429, 429, 429, 429, 429, 429, 429, 429]   ← limit holds
```

Five regression tests added to `backend/tests/api/test_qa_regressions.py`, each confirmed non-vacuous by re-running it against the pre-fix logic:

- forged `X-Forwarded-For` cannot reset an active limit
- a genuine proxy in the trusted list still yields per-downstream-client limiting
- tracked-bucket count stays bounded (500 distinct addresses → ≤ 25 retained)
- `parse_trusted_proxies` discards malformed entries
- the entrypoint does not trust forwarded headers by default (pins the config so this cannot silently regress)

## 9.4 Claims requiring correction

**P2-15 — reported as fixed; partially accurate.** The correlated subquery is genuinely gone, replaced by `LEFT OUTER JOIN`, which removes the per-row subplan (1,060 executions eliminated; 28.5 ms → 24.7 ms). But the accompanying claim *"so `ix_score_total` can be used"* is not borne out — `EXPLAIN ANALYZE` shows the index is still unused:

```
Sort (Sort Key: score.total DESC NULLS LAST)  Method: top-N heapsort
  -> Hash Right Join
       -> Seq Scan on score (rows=1060)
       -> Hash -> Seq Scan on clinic (rows=1060)
```

Structurally better and no longer quadratic in subplan executions, but still O(N) per page. Using the index requires driving the query from `score` (order + limit there, then join back to `clinic`). Treat P2-15 as **partially fixed**.

**P1-8 — labelled "partially fixed"; label is accurate.** Rescore of 1,060 clinics dropped from **27.7 s → 8.1 s** (3.4×) via single-transaction batching and removal of the `get_detail` N+1. It remains synchronous in the request thread, so ~38 s at 5,000 clinics still exceeds a typical 30 s proxy timeout. Unchanged recommendation: move it off the request path.

## 9.6 Revised release recommendation

## ⚠️ Yes, with reservations

Revised from **No**. Both P0s and all seven P1 correctness and security defects are fixed and independently re-verified against live reproductions, and the one defect introduced during remediation has itself been fixed and regression-tested. The system no longer destroys scoring data on transient network failure, cannot be bricked through its own configuration endpoint, and no longer exposes billed third-party operations to unauthenticated callers.

The reservations are operational rather than blocking:

1. **Deployment must set `FORWARDED_ALLOW_IPS` and `RATE_LIMIT_TRUSTED_PROXIES` consistently, and the reverse proxy must overwrite `X-Forwarded-For`.** The defaults are now safe (trust nobody), but a misconfiguration here silently re-opens §9.3. Pre-flight checklist lives in [`docs/how-to/deploy.md`](../how-to/deploy.md).
2. **Set `API_KEY` (and keep `ALLOW_UNAUTHENTICATED=false`).** Auth no longer fails open merely because `APP_ENV` was left at development — empty key without the escape hatch returns `503`.
3. **Rescore stays synchronous.** Acceptable at the 500–1,000-clinic pilot scale the PRD targets; revisit before growing past ~2,000.
4. **Scoring quality is still unvalidated.** Every fix in this round addressed correctness and safety, not detection recall. The PRD's "≥60% of Hot clinics judged worth contacting" metric remains unmeasured, and §2.19's locale/crawl-depth limits still cap signal recall. This is the right next investment — the machinery is now trustworthy enough to evaluate.

Recommended for a **pilot release behind network isolation** with the runbook pre-flight above. Full public production should follow the first measured pilot.
